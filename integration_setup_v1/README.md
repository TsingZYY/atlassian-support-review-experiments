# 帮助免费客户配置集成，会促进付费升级吗？

**这是一个可检验的服务机制假设，目前还不能回答会不会提升升级率。比赛数据支持识别84名“免费套餐快照＋集成主题工单”的候选客户，并已准备20条来源证据卡及10:10的试点分配示例；没有配置协助、配置成功或套餐升级结果，升级率与利润保持未知。**

假设链路是：具体集成配置受阻 → 提供范围明确的配置协助 → 客户完成目标任务并获得价值 → 部分客户产生有依据的付费需求。每个箭头都需要验证。当前不是已证实的增长方案，也不是通过套餐与集成的强关联反推升级因果。

## 1. 已从比赛数据核对什么

筛选规则在本轮固定为客户表`Plan Type=Free`且工单`Ticket Subject=Integration`。不额外要求零使用、低满意度、技术类型或未关闭状态，以免将这些代理当作确认需求。按规范化邮箱关联客户，沿用任一工单姓名、年龄或性别冲突时剔除整客户的规则。

| 检查项 | 结果 | 含义 |
|---|---:|---|
| 客户表记录Free | 1,472人 | 静态套餐快照，不是套餐历史 |
| 身份一致的Free客户 | 1,440人 | 候选占比的分母 |
| Free＋Integration主题，未排冲突 | 89人 | 初始候选 |
| 排除冲突后 | **84人** | 占上述1,440人的5.83% |
| 同工单产品1—5月使用记录完整 | 84人 | 每月一条，不混入其他产品 |
| 至少一个月集成使用量大于0 | **84人** | 不能全部称作“从未用过集成” |
| 五个月均为0 | 0人 | 不代表当前配置任务已经成功 |

产品分布：Bitbucket19、Trello19、Confluence17、Loom15、Jira14。状态为Closed32、Open27、Pending25；只有32条有评分。工单类型还包括Billing18、Product inquiry17、Refund13、Cancellation19、Technical17。因此`Integration`只能指向一个主题，**不能确认84人都有未解决的配置需求**。

全名单见[candidate_roster.csv](candidate_roster.csv)。原始数据没有客户对具体配置任务的描述，也没有配置成功事件。`Closed`不能替代配置成功；`Integrations Used>0`不说明当前想连接的系统、当前任务是否完成或客户是否需要付费能力。过去月度使用记录也不能构成接受配置帮助后的结果。

## 2. 为什么可能提高升级，也可能不提高

以下均为待检验机制，不是本轮观测结论：

| 机制假设 | 应观察的结果 | 不支持机制的结果 |
|---|---|---|
| 配置障碍阻止客户获得价值 | 提供帮助后，明确的目标配置任务完成率上升 | 完成率不变或返工增加 |
| 体验到价值后出现付费需求 | 被分配帮助的客户后续付费升级率上升 | 配置成功增加，但升级率不变或下降 |
| 增量升级覆盖服务投入 | 每名分组客户的净贡献提高 | 升级增加，但支持成本超过新增贡献 |

一种可能是成功配置帮助客户看到价值，随后产生新的付费需求；另一种可能是免费功能已满足需求，配置成功后客户继续免费使用。还可能原本就准备升级的客户更主动寻求帮助。当前字段无法判断哪条机制成立。

不能假设任何具体产品的集成数限制、付费功能或官方价格；这些信息不在比赛字典中。确认真实付费原因是机制研究的一部分，不应从套餐和使用量直接生成推销结论。

## 3. 已准备的20条小试点

从84人中每产品按固定客户ID哈希选4人，共20人。另一个固定哈希在每产品4人中预分配2人到配置协助、2人到现行支持，总体10:10。[20条证据卡](evidence_cards_20.json)保留工单行号与同产品五个月使用的行号；[预分配表](planned_pilot_20.csv)明确标为`PREPARED_NOT_EXECUTED`，结果为空。

**这是试点设计示例，不是已实施随机试验。** 所有候选尚未确认当前Free身份与具体配置需求。真实执行时必须先确认任务和资格，再随机分组；不能根据当前预分配结果决定保留哪些人。若真实资格改变，应建立新的冻结合格名单与分配，不把这份演示表包装成已完成试点。

同一客户只进入一个组；按产品分层，以提供帮助这一服务方案为比较对象：

- **协助组：现行支持＋主动提供一次范围明确的配置协助。** 在分组前记录目标接入系统、任务及成功标准，不替客户虚构需求。
- **对照组：维持现行支持。** 两组保持相同定价与升级促销条件，避免把优惠促销效果混入配置帮助效果；正常支持照常提供。

主要结果预设为**分组后30日内的付费升级率**。7日内配置任务成功率作为机制指标；服务投入和退款作为利润计算依据。7天与30天是设计选择，不是源数据已有观察窗口。满意度可作辅助观察，不能代替升级。

结果按最初分组统计全部客户，包括拒绝帮助、未完成配置和未升级的人。**不能事后仅比较“成功配置的人”和“未成功的人”**，否则主动性、原始需求及其他差异会混入服务效果。未获得结果记录也不能直接填为未升级；须报告缺失并做缺失影响分析。

20人能验证流程及测量是否可执行，效果估计可能很不稳定。必须报告实际人数、差异和不确定性，不保证能检出升级提升。当前没有任何真实客户联系、配置操作、计时或付费结果。

## 4. 升级与利润怎样衔接

先判断主动提供配置帮助是否提高升级率，再核算升级净贡献能否覆盖协助成本。不要仅看协助组有多少人升级，对照组用于估计其中有多少本来就会升级。

`增量升级率 = 协助组30日升级比例 − 对照组30日升级比例`

在假设每次升级新增净贡献相同为M、每人额外帮助成本为c、计划覆盖N人且新增固定成本为F时：

`条件净收益 = N × (增量升级率 × M − c) − F`

M应扣除退款及新增服务等变动成本；金额不同则直接比较每组实际平均净贡献。当前没有M、c、F、升级结果或帮助效果，因此不填假数字输出“预计实际利润”。若另做情景模拟，正、零、负增量都须保留，参数与实测结果分开。
