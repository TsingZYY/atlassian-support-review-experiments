# 仅比赛数据：客户信息是否改善低满意度识别

**结果：本轮没有支持该假设。加入客户画像与使用信息后，20条留出案例的概率误差没有下降，且未胜过简单常数基线。** 这不是证明所有方法都无效，而是当前固定方法和样本未显示增量。

## 数据、假设与验证闭环

全部观测来自比赛三张原始合成CSV；新造案例数为0。结果标签直接读取Customer Satisfaction Rating：1—2分为低满意度，3—5分为另一类。没有使用外部知识库、自编客户回答或假设的解决概率。

假设：在数据一致、月份完整、已关闭且有评分的客户中，加入客户画像及同产品1—4月使用快照，能够比仅使用工单字段更准确识别低评分。

先固定[协议](protocol.md)和[参数](protocol.json)，按客户哈希划分，开发集选好模型后保存[定版参数](model_freeze.json)，再计算20条测试案例的指标。算法和数据哈希在[冻结记录](execution_lock.json)中。

| 样本步骤 | 工单数 |
|---|---:|
| 原始工单 | 8,469 |
| 已关闭、评分合法 | 2,769 |
| 排除客户身份字段冲突后 | 2,663 |
| 再排除1—4月使用值不合法后 | 2,644 |

2,644条对应2,644个不同客户。训练2,100条，开发524条，最终测试20条，客户互不重叠；最终测试含6条低评分和14条非低评分。测试样本按固定哈希选择，没有按评分分层、换样或挑有利案例。名单见[split_manifest.json](split_manifest.json)。

三个对照使用同一人群：训练集低分比例常数；工单字段模型；工单字段加客户画像与使用信息的模型。后两者使用同一逻辑回归和预设正则网格，由开发集指标选定，最终都选中0.1。

## 测试结果

| 方法 | Brier概率误差（越低越好） | AUC | 0.5阈值正确数 |
|---|---:|---:|---:|
| 训练集低分比例常数 | 0.21819 | 0.5000 | 14/20 |
| 仅工单字段 | 0.21680 | 0.4524 | 14/20 |
| 工单＋客户画像＋使用记录 | 0.21843 | 0.5000 | 14/20 |

加入信息后的Brier改善量定义为“工单模型误差－完整模型误差”，本次为**−0.00163**，即误差略升。20客户配对重抽样的95%区间为**[−0.01280, 0.01023]**，跨过0。预设要求改善至少0.02、区间下界大于0且胜常数基线，均未满足。

三种方法在0.5阈值下均未识别出低分案例，所以14/20准确率只体现多数类比例，不能称为模型有效。前5名低分数量仅作附录：常数模型的排序完全来自Ticket ID的任意并列规则，不能据此推断常数模型有排序能力。

[20条逐例预测与原始评分](test_cases_20.csv)包含全部概率和配对误差，便于逐条查回原CSV；[机器可读结果](results.json)保留开发选择、质量过滤和门槛结果。Bootstrap只重复抽取这20条索引，不制造新客户或标签，也不增加独立样本。

## 反馈后的决定与边界

本轮判定为 `NOT_SUPPORTED_BY_THIS_TEST`。不在这20条上反复修改模型直到通过；当前不把客户画像/使用辅助低分识别作为已有效的核心卖点。后续若提出其他假设，必须继续以比赛中实际存在、可核对的字段和结果为依据，并另行记录协议及数据复用。

没有可信的工单创建/评分时间，因此这只是回顾性识别，不是事前预警，也不是干预因果效应。人群仅含合法完整、已关闭有评分客户；不能外推到未关闭工单。比赛数据本身为合成数据，评分不等于工单是否真正解决。20条留出样本很小，阴性结果不等同证明零效应。

## 运行

从仓库根目录运行：

```bash
python csat_context_v1/experiment.py
```

依赖现有requirements.txt中的NumPy；CSV读取、哈希和样本划分使用Python标准库。复跑核查冻结文件哈希，重建相同划分与模型。时间戳会更新，关键结果应一致；代码或协议变更须建立新版本并说明原因。
