# 客户体验与情绪方向：哪些已经验证，哪些尚不可测？

**建议保留截图中的客户体验方向，并将当前小模型定位为“已观察满意度的证据复核”。比赛字段不足以直接验证客户语言情绪识别；固定的解决记录词袋检验没有改善低评分识别。原型已能展示评分与原始工单、保留未知，但保护利润或改善客服结果尚未验证。**

本轮只使用比赛合成CSV和字段字典，没有生成客户话语、情感标签或恢复结果。截图中的问题作为项目目标；不根据聊天截图另行推断比赛评分要求。

## 1. 原始数据能支持真正的sentiment分析吗？

工单表16列中，没有客户正文、聊天对话、客户原话或情感标注字段。`Ticket Subject`全部落在16种主题标签内，例如Integration、Payment issue、Software bug；主题不等于客户的情绪。

`Resolution`按原字典是解决记录，未说明作者为客户。它有2,769条非空文本，每条3—8个英文词，而且2,769条全部唯一；数字归一化后仍全部唯一，不能宣称通过模板去重证明这些文本无用。

原文样例包括：

> Wish board same manage mission.

> Western leg involve.

这些句子本身不足以定位具体问题、处理动作或客户感受。固定20条来源样例中，15条有文本，5条缺失；AI逐条审核在15条可用文本中，分别未辨认出明确的问题细节、解决动作或感受表达（各0/15）。见[文本审阅](text_review.md)。本审核省略输入评分列，但并非完整盲法，也没有人工验证的情感真值。没有文本的样例保留为不可审计，样本判断不推及全部非空文本，也不能当作真实情感训练标签。

因此，直接把主题标签、解决记录中的孤立情绪词或满意度评分转写成“客户生气/开心”，缺乏相应证据。3分不是已验证的中性情绪，1—2分也不告诉我们不满意的具体原因。

## 2. 实际跑了一个固定的文本检验

为了检验解决记录中是否仍有可用信号，以原CSV的1—2分为低满意度标签，尝试用Resolution词袋区分低评分。**这是已关闭工单内文本与评分的事后关联检查，不是客户情感识别，也不适用于未关闭工单。**

排除跨表身份冲突后保留2,663名已关闭有评分客户。固定客户哈希划分为训练2,130人、测试533人；测试204人低分。只用训练集构造971词词表，采用固定alpha=1的Multinomial Naive Bayes，没有外部情感词典、模型调用或后续调参。与训练低分比例常数基线比较。

| 方法 | 测试Brier误差（越低越好） | AUC | 0.5阈值准确率 |
|---|---:|---:|---:|
| 训练低分比例常数 | **0.23650** | 0.5000 | 61.73% |
| Resolution词袋模型 | 0.29740 | 0.4846 | 54.03% |

词袋的误差改善量为 **−0.06090**，5,000次测试客户配对重抽样的95%区间为 **[−0.08075, −0.04096]**。当前方法比基线更差，未显示低评分识别增量；测试词全部在训练词表中，结果不是由未知词造成的。该区间以本次划分和已拟合模型为条件，不包含重新训练或方法选择的不确定性；比赛数据已在前序研究中使用，本轮属于回顾性检验。

这不证明所有文本算法都无效，但没有理由把这个已运行方法宣传为有效的情绪识别模型。即使将来某种文本模型预测评分更好，仍需客户语言和独立情感标签，才能验证“识别客户情绪”。由于Resolution与评分只在Closed出现，不能将本检验写成处理中或事前预警。

## 3. 已跑通的小模型：评分证据与复核入口

全8,469张工单按原评分保留以下四种证据状态：

| 原始证据 | 工单数 | 原型行为 |
|---|---:|---|
| 1—2分 | 1,102 | 已记录低满意度，进入待复核清单 |
| 3分 | 580 | 保留中间评分及来源 |
| 4—5分 | 1,087 | 保留高评分及来源 |
| 无评分 | 5,700 | 标记反馈未观测，不补标签 |

有评分的2,769张仅占全表 **32.70%**；无评分占67.30%。已评分中低分占39.80%，不能称为所有客户的不满意率。

输入Ticket ID，原型返回原始主题、类型、提交渠道、状态、评分、CSV行号和建议核实的问题。所有工单的客户语言情绪均标记未知；不会把无评分默认为中性、把Closed当满意，或从套餐/集成数量推导情绪。

例如固定样例[票5919](example_low_5919.json)为低评分，进入`REVIEW_REPORTED_LOW_CSAT`；[票6863](example_unknown_6863.json)无评分，返回`FEEDBACK_NOT_OBSERVED`，情绪与业务结果仍未知。两份输出均通过实际CLI运行和独立来源核对。评分映射正确属于实现检查，不能写成“情绪识别准确率100%”。没有自动发消息、改变工单或向客户推荐付费。

```bash
python sentiment_evidence_v1/experiment.py --ticket-id 5919
python sentiment_evidence_v1/experiment.py --ticket-id 6863
```

## 4. 如何形成业务验证闭环

当前已完成的是：题目目标 → 字段/文本来源审查 → 固定文本对照试验 → 保留不支持结果 → 实现评分证据原型 → 核对20条来源和全表未知处理。

该原型提供一个可执行的客户体验复盘入口。下一步若有原始反馈或评审条件，可检验“展示这张证据卡是否帮助人更准确说明客户哪里不满意、提出有依据的下一步”；记录正确引用、缺失保留、错误归因和复核耗时。不能凭低分直接填入原因，也不能把完成卡片当作客户问题已解决。

改善实际满意度、挽回客户、减少成本或保护利润，还需要干预与对照后的真实结果。**这些业务步骤均为CANDIDATE-UNRUN，不是本轮测得的收益，也不是完成比赛方法展示的前提。** 套餐—集成的强关联可作为背景证据，但本轮不会用它替代缺失的客户情绪或业务结果。
