# 工单复核决策模型

这是比赛用的最小可运行规则模型，版本 `review-rules-1.0`。只完成一个任务：汇总工单与使用证据，判断是否建议进一步人工复核，并交代依据和缺失信息。模型类型为确定性决策树，无需训练或付费 API，仅依赖 Python 标准库。

## 输入与输出

输入来自比赛三张表：客户关联、工单状态/优先级、对应产品的连续五个月活跃天数。输出保留来源 ID，不导出姓名、邮箱、年龄或性别。姓名等字段只用于跨表一致性检查。

```text
工单 + 使用记录
  → 数据核对
  → 固定规则判断
  → 结论 + 计算依据 + 信息缺口 + 待验证下一步
```

| 输出 | 含义 | 下一步 |
|---|---|---|
| DATA_CHECK | 数据关联冲突、月份缺失/重复或活跃天数越界等 | 先核对数据；原有支持照常继续 |
| REVIEW_CANDIDATE | 未关闭且 High/Critical，同时最近两个月低使用 | 核实原始问题与既有追问，必要时询问使用减少原因 |
| STANDARD_SUPPORT | 未满足这条复核规则 | 沿用现有工单流程，不能据此降级或断定健康 |

“进一步复核”是建议，不是自动提高优先级、发消息、关闭工单或执行修复。缺少真实问题正文时，模型不编造解决步骤。

## 唯一核心规则

每月活跃率 = Active Days / 当月日历天数。

前 3 个月的活跃率均值记为 B。后 2 个月必须各自同时满足：

- 当月活跃率 ≤ 0.70 × B；
- B − 当月活跃率 ≥ 0.10，即至少下降 10 个百分点。

再结合“工单未关闭且 High/Critical”输出复核候选。数据检查优先于规则计算。阈值等号计入，数值容差为 1e-12；零基线不会仅因相对条件产生告警。

默认使用 2023 年 1—5 月记录，搭配所提供的工单快照。工单状态对应较后的时间，所以这是快照复核，不能当作 4 月实时预警。`--as-of` 只选择使用月份，不把工单状态变成历史时点数据。

## 运行

在此目录运行：

```powershell
python model.py
python model.py --ticket-id 6545
python verify.py
```

如果系统使用 `python3` 或 Windows 的 `py` 命令，请以相应解释器替换 `python`。

批量输出保存在 `outputs/predictions.json`；摘要为 `outputs/summary.json`。单个 Ticket ID 返回一张 JSON 证据卡。修改数据位置可用 `--data-dir`，修改输出位置可用 `--output-dir`。

## 一个已跑通的例子

合成工单 6545：Trello，Network problem，Open，Critical。客户 1—5 月活跃天数为 7、6、5、3、2 天。基线活跃率约 20.05%，4 月为 10.00%，5 月为 6.45%，两个月均符合相对和绝对下降条件。

模型输出 `REVIEW_CANDIDATE`，附上逐月计算，要求先核实问题原话及已尝试动作，再视需要询问使用变化。现有字段不能证明网络问题造成使用下降，也没有处置后效果。见 `outputs/example_ticket_6545.json`。

## 已完成哪些验证

- 全部 8,469 张工单都有输出：347 张 DATA_CHECK，43 张 REVIEW_CANDIDATE，8,079 张 STANDARD_SUPPORT。
- 347 是工单数；它们涉及上轮质量排除的 198 名客户，不能把这两个数混为同一口径。
- 20 条冻结样例逐条通过原始字段、跨表关联、月度占比与规则结果核对；10 对样例的产品、套餐、优先级和状态相同。样例包含 10 条规则命中和 10 条未命中，不是随机干预两组。
- 全量 43 条候选与之前独立验证保留的候选集合一致。
- 10 个边界检查通过：阈值等号、零基线、关闭工单、低优先级、只下降一个月、缺月、重复月份、越界天数、身份冲突及使用记录关联错误。

原始文件哈希保留在摘要中；运行 `verify.py` 可复查，明细为 `outputs/verification.json`。这些检查证明实现与定义一致，不是预测准确率或解决率。

## 比赛中的证据边界

| 主张 | 目前证据 | 可用表述 |
|---|---|---|
| 规则能完整执行、输出可追溯 | 全量执行、20 条来源核对、10 个边界检查 | 已实现并验证 |
| 能筛出规则定义的复核候选 | 全量 43 条结果可复算 | 描述性筛选结果 |
| 能识别时间顺序特有的持续恶化 | 原始命中倍数约 2.70；打乱月序均值约 2.69，p=0.466 | 未通过原先证据门槛，不作该宣称 |
| 使用信息能改善客服判断 | 20 条 AI 审计未找到新增的确定修复依据 | 待检验的设计假设 |
| 提升真实解决率、留存或收入 | 无实际干预及后续结果 | 不可报告；列入赛后验证计划 |

月序检验保留客户间差异及共同基线效应，月份可交换只是近似假设。该结果不能推出所有相关信息都不存在，但足以阻止把目前规则包装成已验证的动态预警。

## 比赛故事如何保持完整

设计问题：能否把分散的工单和使用事实变成可解释的复核输入？这是设计目标，目前未证实客服的真实时间损失或需求规模。

数据证据 → 一个规则模型 → 一张具体证据卡 → 可重跑的核对与边界检查 → 未通过的预测检验及明确局限 → 赛后比较常规支持与信息辅助支持的判断、耗时和真实解决结果。

比赛阶段完成的是这个方法闭环。真实客服试点属于后续实施计划，不是比赛交付的前置条件；原有 20 条真实试点文档仅作为可选附录。当前业务价值缺口保留：正确汇总和筛选，不自动证明新增信息有用。
