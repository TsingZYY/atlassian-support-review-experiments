# 第二轮利润验证：付费机会证据完整性

本轮问：对原工单中具有泛化产品咨询/推荐标签的Free客户，加入客户表和使用表，能否得到足以支持具体付费建议的新证据？此前高协作筛选未获清晰支持，不更换样本或代理指标继续追逐显著性。

数据仅为三张比赛合成CSV和字段说明。分析前已观察全表类别交叉分布及8条可行性记录，因此本轮是探索性来源审计，不是盲测或业务干预实验。

## 固定样本

客户邮箱去空格、忽略大小写后唯一匹配。沿用既有保守规则：任一关联工单姓名、年龄或性别与客户表冲突，则排除整个客户。候选当前套餐为Free，工单类型为Product inquiry **或** 主题为Product recommendation。不按状态、使用量或审核结论筛选。

每产品按 SHA256((hash_salt + '|' + Ticket ID).encode('utf-8')).hexdigest() 升序取4条，共20条。源客户必须唯一，否则停止并另立协议，不悄悄重抽。固定名单、原始输入及代码/协议/数据哈希后审阅。

20条用于覆盖五个产品的来源核验，不是全体客户的代表性转化样本。所有候选数量仅描述完整可用源表，不是市场机会规模。

## 同一20条的两种信息视图

A仅原工单非身份字段；B加入客户的当前套餐/公司规模/行业/区域及1—5月原始使用。身份字段只用于关联，不作为商业理由。时间记录和套餐快照不能当作已知的历史干预特征。

审核维度：

1. 具体需求：原字段是否明确表达客户要完成的任务或具体阻碍。泛化类别/主题不等于完整需求。
2. 明确购买或升级意愿：须有原字段直接证据，高使用或Free不能代替。
3. 付费能力匹配：须有具体需求与相应付费套餐能力的来源依据，不使用外部套餐限制。
4. 利润依据：须有收入、成本、相对对照的转化增量等，不能用使用量代替。

状态为PRESENT、ABSENT_FIELD或NOT_ESTABLISHED。未知不代表客户没有需求。若PRESENT必须逐字引用来源，并说明支持关系；每项保存理由。加入背景信息与付费理由证据覆盖分别报告。不给20条覆盖检查做p值，不把AI审核标签当真实购买结果。

主代理逐条审阅后由独立代理复核；两者均为来源证据审查，不是销售/客户人工试验。审核结论作为有来源说明的派生注释保存，未经原字段支持不得补造结果。

## 最小可执行输出

退款/取消类别或主题存在 → SUPPORT_FIRST，先核实处理请求。
否则双字段同时为产品咨询与产品推荐 → REQUIREMENT_REVIEW，确认具体需求。
其余泛化线索 → CLARIFY_REQUEST，先分清选型、使用或账务问题。

这些是公开的保守流程规则，不是学得的最优策略。输出原始依据、补充的使用背景、仍缺的证据和一条待确认问题；不生成假客户回答，不直接推荐套餐或金额，不发出任何客户消息。

如果两视图均无法支持付费建议，则本假设未得到支持。保留小模型的来源追踪与澄清用途，利润增量保持未知；不以路由正确率冒充收益。
