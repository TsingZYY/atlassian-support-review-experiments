# 第二轮利润验证：客户背景能否补出具体付费理由

**20条已核验。加入客户画像及五个月使用记录，补充了背景，却没有在这20条中补出足以支持具体付费建议的证据。购买意愿和利润增量仍未知。**

这次验证的是“已有证据够不够支撑下一步商业建议”，不是客户是否愿意付费的试验。此前高协作名单的20条比较未获清晰支持；本轮转向更接近商业决策的证据完整性，不再换代理指标寻找显著结果。

## 假设与固定20条

假设：对带有产品咨询/推荐标签的Free客户，结合客户背景与使用记录，能够提供比仅看工单更具体的付费理由。

身份一致的Free客户有1,440人。其中313条工单类型为Product inquiry，82条主题为Product recommendation，18条同时符合，因此并集为 **313 + 82 − 18 = 377人**。这些是泛化咨询标签，不是377个已确认购买机会。

| 产品 | 泛化线索候选 | 固定核验记录 |
|---|---:|---:|
| Loom | 80 | 4 |
| Trello | 69 | 4 |
| Bitbucket | 58 | 4 |
| Confluence | 91 | 4 |
| Jira | 79 | 4 |

每产品按预先固定的Ticket ID哈希取4条，合计20条，未按状态、使用量或审核结果挑选。记录包括已关闭工单，是历史来源核验，不是现在应联系的名单。协议、源哈希和名单均保留。

## 两种信息视图的核验结果

A为原工单；B为同一工单加当前套餐、公司背景和1—5月使用记录。主代理逐条检查后，独立代理从原CSV重新核对并独立审阅，结论一致。这是AI来源审查，不是客户回答、销售人工标签或实际转化结果。

| 核验项 | A：仅工单 | B：补充客户与使用 | 解释 |
|---|---:|---:|---|
| 当前套餐及五个月使用背景 | 工单表未提供 | 20/20有记录 | 背景信息确实增加 |
| 足以支持付费理由的具体任务或阻碍 | 0/20可确认 | 0/20可确认 | 有泛化主题，但缺少明确任务、期望结果与阻碍细节 |
| 明确购买或升级意愿 | 0/20可确认 | 0/20可确认 | 全部未知，不能解释成没有意愿 |
| 需求与付费套餐能力的匹配依据 | 缺少相应字段 | 仍缺少相应字段 | 当前套餐名称不提供功能限制或升级价值 |
| 利润计算依据 | 缺少相应字段 | 仍缺少相应字段 | 缺少转化对照、收入与成本 |

0/20表示未找到符合既定定义的支持证据，不是“客户需求为零”或“转化率为零”。这20条用于五产品来源覆盖，不估计377人的有效率，不做显著性检验。

## 两条能直接追溯的例子

- **PE2-09 / 工单2602，Bitbucket**：类型Product inquiry，主题Integration，状态Pending Customer Response。补充记录显示2023年5月Collaborators=19、Integrations Used=0。可以据此确认希望连接哪个系统、遇到什么阻碍；无法推断客户达到Free限制、19个付费席位或已愿意升级。
- **PE2-08 / 工单8017，Trello**：主题Product recommendation，但类型Cancellation request，状态Pending Customer Response。模型先核实取消相关请求，不能只因“产品推荐”标签就直接给付费建议。

源行和逐月原值见[20条记录包](case_packets_20.json)；各项判断及原字段引用见[逐条审核](audit_annotations.json)。

## 小模型的实际输出

模型已运行，输入原工单和关联记录，输出来源、已知背景、未知证据及待确认问题：

| 输出 | 20条中的数量 | 规则用途 |
|---|---:|---|
| CLARIFY_REQUEST | 17 | 先分清选型、使用或账务问题 |
| SUPPORT_FIRST | 2 | 先核实记录中的退款/取消请求 |
| REQUIREMENT_REVIEW | 1 | 两个咨询标签一致，继续确认具体需求 |

这些规则是可审核的流程选择，不是已证明最优的销售策略。模型没有发出客户消息、生成客户回答、推荐具体付费套餐或计算虚构收益；[20条完整输出](model_outputs_20.json)中的相关业务结果均保留为未知。

## 研究决定

本轮没有支持“补充现有客户背景，就能确定具体付费理由”的假设。两轮结果共同说明：在当前比赛数据中，从使用量或泛化咨询标签直接跳到付费推荐，缺少关键证据。

利润方向保留，比赛的小模型收敛为 **利润机会审查助手**：整理原始证据 → 区分待核实的支持问题与咨询 → 输出一个需求确认问题 → 将尚缺的转化与成本参数列明。它能展示可执行、可追溯的方法；“问得是否更好、客户是否付费、利润是否增加”均尚未被本数据验证。

后续仍仅使用这三张数据时，不再把协作人数、工单类别或路由数量包装成新的利润结果。可继续验证的部分是来源正确性、规则覆盖和方案可执行性；真实商业效果保持未知。

## 复现与审计

```bash
python profit_evidence_v2/experiment.py
```

脚本仅依赖Python标准库，验证代码/协议/源文件/冻结名单与审核输入一致，再生成结果。审核注释是从原记录形成的可审查派生判断，重跑脚本复现的是这些判断的汇总，不等于重新完成独立语义审阅。

首次准备阶段的统计字段修正记录在[说明](preparation_note.md)，原准备哈希完整保留。没有更换样本或隐藏不支持的结果。[独立复核](reviewer_notes.md)记录逐条来源及判断。

三张合成CSV和[字段说明](../data/README.md)是唯一数据来源。静态套餐时点、抽样框架和生成机制未知；20条全有可读取的五个月使用，原使用字段范围检查未发现异常。这只说明这些记录可追溯，不构成付费或利润效果证据。
