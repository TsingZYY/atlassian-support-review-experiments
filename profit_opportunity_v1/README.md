# 当前方向：研究怎样增加利润

**先研究 Free 客户的付费需求线索。首轮20条原始记录已完成，单靠历史协作人数筛选，未显示清晰的下月协作使用优势；实际付费及利润增量仍不可识别。**

## 为什么选择这个切口

目标是增加利润，而不是把低活跃、工单关闭或取消请求当作最终成功指标。当前三张比赛合成CSV可以支持的路径如下：

| 路径 | 可用证据 | 当前不能验证的部分 |
|---|---|---|
| Free 转付费、已有套餐扩销 | 当前 Plan Type、月度协作人数/集成/使用 | 未来升级、付费意愿、套餐功能限制、价格和增量贡献 |
| 留存保收 | 取消请求类别、使用变化 | 实际续费、实际流失、挽回的收入 |
| 客服降本 | 工单类别、状态、部分时间戳 | 实际人工工时、单次成本、自动解决率 |

选择 Free 客户需求筛选，是因为客户和使用表能形成一个简单可执行的名单模型；不是因为已证明它优于其他利润策略。此前五产品取消请求比较未显示清晰差异，不能据此选定“最容易流失的产品”做利润承诺。

## 假设 → 实验 → 结果

假设：当前记录为 Free、1—4月协作人数较高的客户，在5月仍有较强协作使用，可以作为后续了解付费需求的线索。

原客户表共8,320人，其中Free 1,472人。沿用既有身份一致的保守队列，排除32名与工单身份字段冲突的Free客户，剩1,440人。产品人数为Loom 276、Trello 290、Bitbucket 241、Confluence 329、Jira 304。不根据Active Days或5月协作结果筛选名单。

每产品按1—4月平均 Collaborators 取最高2人，共10人；再从剩余客户中固定哈希抽取2人，共10人作比较。20人唯一、不重复，没有客户被实际触达。哈希精确约定为 `SHA256((hash_salt + '|' + Customer ID).encode('utf-8')).hexdigest()`，排序使用十六进制字符串升序；优先组分数并列时也按此顺序。固定盐见[协议](protocol.json)。

名单和输入特征在本轮代码读取5月结果前写入[冻结名单](selection_freeze.json)。之前的研究已看过此数据集，所以本轮是回顾性检验，不是确认性盲测。

## 研究决定与利润闭环

1. **保留利润增长为主目标。** 本轮验证了名单生成、来源追踪和后续协作对照的计算流程，未验证优先名单的商业价值。
2. **不直接采用“历史协作最高”作为已验证的销售优先规则。** 保留这次不确定结果，不换20人重跑到显著，不将Bitbucket的小样本正差异作为产品结论。
3. **下一步先定义付费理由。** 在比赛交付中，可以展示“客户证据 → 待确认的需求 → 可审核建议 → 收益与成本核算”的小模型。当前缺少客户具体需求、套餐功能限制及实际升级，付费理由只能标为待确认，不由协作人数自动推出。

统一周期下的利润接口为：

`增量利润 = N × (相对对照的增量付费概率 × 每次转化的净贡献 − 单次触达增量成本 − 每人其他预期损失) − 固定实施成本`

净贡献应扣除新增服务、交付、退款等变动成本；增量概率须扣除原本会自然付费的人。若N和净贡献为正，盈亏平衡要求：

`增量付费概率 > (单次触达增量成本 + 每人其他预期损失 + 固定实施成本 / N) / 每次转化的净贡献`

比赛数据没有这些财务参数，结果JSON明确为未知，不能代入自造价格/成功概率再宣称实证收益。比赛可以交付可执行、可核验的方案，不需要伪造实际工单或客户试验。

## 适用范围与复现

- Free是静态套餐快照，无法证明客户在1—4月当时的套餐；此结果也不是未来升级预测。
- Collaborators不是付费席位或购买意愿，较多协作者不代表超出任何真实套餐限制。
- 合成数据生成机制和抽样框架未知，全部客户都有支持工单，结论只限当前样本。
- 仅有20条检验记录，未取得客服/销售人工判断、真实客户反馈或实际触达结果。
